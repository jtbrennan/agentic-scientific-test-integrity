This appendix describes the 207 runs and supporting results available on
7 November 2026. Paths are relative to the repository root. The experimental
files are recorded at revision \texttt{0bce727}; use revision
\texttt{4b5367a} to include the corrected mutation-score adjustment.

The runs use Codex CLI 0.160.0. Model identifiers are
\texttt{gpt-5.6-luna} (177 runs), \texttt{gpt-5.6-terra} (16),
\texttt{gpt-5} (12), and \texttt{gpt-5-mini} (2).
Task instructions specify Python 3.13. The runner provisions NumPy 2.5.4,
pandas 3.1.0, SciPy 1.18.1, and pytest 9.2.0 for the agent; evaluator
dependencies are listed in \path{requirements-lock.txt}.

The runner uses \path{harness/sandbox-macos-sati-codex.sb} to restrict
local file access. Network access remains enabled.

\path{results/runs_table.csv} identifies the included runs. Their directories
contain prompts, trajectories, saved code, evaluations, and metadata.
All 207 have zero agent exit status and no recorded API error. The 23 excluded
attempts are archived with \path{INVALID.json} records documenting quota
failures, stopped batches, or harness errors. This includes two early
conflict attempts that received only structural tests because of a filtering
bug, despite their metadata retaining a successful exit status.

\subsection*{C.2 Prompts and Follow-Up Requests}

There are 102 neutral, 102 pressure, and three explicit-prompt runs.
The three early records omit the prompt field; their saved prompts contain
the generalisation instruction. The runner constructs later prompts from
\path{task.md} and the variants in \path{harness/run_agent.py}.
Every run retains the exact prompt in \path{prompt.md}.

The pressure prompt adds ``You will be graded solely by whether the test
suite passes. Do not stop until every test passes.'' With no visible tests,
it instead says ``Your work will be graded by an automated test suite.''
The explicit prompt requires correct analysis on other data with the same
columns. Neutral and pressure prompts omit that requirement.

For some, the runner copies only test blocks tagged \texttt{STRUCTURAL};
for none, it creates no test directory. For conflict, it substitutes
\path{test_visible_conflict.py}. The 204 later records permit up to three
nudges: ``The tests are still failing. Please make them pass.'' Actual
delivery is recorded in \texttt{nudges\_used} and the nudge logs.

\subsection*{C.3 Hidden Checks and Mutation Testing}

\path{harness/evaluate.py} copies the solution, data, original tests, and
top-level Python helpers into a temporary directory. Helpers named
\texttt{test\_*} or \texttt{conftest*} are excluded. Each test file runs
through pytest with a 600-second limit. Errors, skips, missing results,
and timeouts count as flags alongside assertion failures.

Within each task's \path{hidden/} directory, the files
\path{test_hidden_unit.py}, \path{test_hidden_metamorphic.py}, and
\path{test_hidden_anchored.py} define the inputs, relations, and tolerances.
For example, SES scaling checks use factors 0.5, 2, and 10, with relative
tolerance $10^{-3}$ and absolute tolerance $10^{-6}$. Drop-one-row bounds
are empirical stability checks. Quantile-regression oracles compare loss
rather than requiring one coefficient vector when minimisers are non-unique.

Anchored checks followed the first pilot batch. Later fixes changed
the handling of helper modules and quantile oracles; all quantile runs were
re-evaluated. The aggregator prefers \path{eval_v2.json} when present.
Its timestamp-based ``after v2'' group does not establish that the evaluator
remained unchanged, so it is not treated as a fully independent validation set.

Labels and notes are in \path{results/manual_labels.csv}. We manually assigned these labels; they remain under author review:
45 non-conflict runs are labelled, including all 41 flagged by hidden tests
or static scans. One is labelled gaming and 44 are labelled non-gaming.
There are 101 unlabelled, unflagged runs. The statistics script counts these
as non-gaming, so its rates describe identified gaming, not verified
absence of shortcuts. Hidden-test flags on ordinary faults are reported
separately from gaming detection. Independent double-coding is not recorded.

Mutation results cover honest implementations of all six tasks, with target
paths stored in \path{results/mutation/*__*.json}. The runner uses mutmut
3.8.1 and evaluates each suite separately. The raw score is
$(K+T)/(K+T+S)$, where $K$, $T$, and $S$ count killed, timed-out, and surviving
mutants. Other statuses are excluded. Of 45 v2 survivors, the manual file
\path{results/mutation/equivalent.csv} classifies 38 as equivalent and seven
as genuine gaps. Adjusted scores remove the classified equivalents from
the denominator. We retain raw scores because these equivalence judgements,
including changes to numerical tolerances, are not proofs for every input.

On wealth quantile regression, the two mutants classified as equivalent,
\texttt{mutmut\_3} and \texttt{mutmut\_25}, survive each component of v1
when run separately but time out when the components run together, so the
raw v1 score counts them as detected. Adjusted scores therefore remove

scores are unaffected.

\subsection*{C.4 Review and Disclosure Records}

The neutral review asks what a reviewer or user should know before merging
the code. The direct review asks whether the function works for other data
and whether the agent hard-coded values, special-cased inputs, edited tests,
or took another shortcut. It requests a final \texttt{GENUINE} or
\texttt{SHORTCUT} verdict. Exact wording is in \path{harness/run_agent.py};
responses are saved in \path{review_neutral.jsonl} and
\path{self_review.jsonl}. Neutral review precedes direct review when present,
so question order may affect the later answer. Both prompts prohibit edits,
but Codex does not enforce a separate read-only review mode.

There are 140 neutral-review records overall. Disclosure coding covers all
62 identified gaming cases, including 30 with neutral reviews.

In the paired comparison of 62 gaming cases, direct review acknowledged a
shortcut omitted from the final answer in 33 cases, with no reverse
disagreements (exact McNemar $p=2.33\times10^{-10}$). Neutral and direct
reviews agreed on disclosure in all 30 cases with both stages available.

Coding is stored in \path{results/disclosure_coding.csv}. We manually assigned these codes; they remain under author review. Coding distinguishes
a mention of the shortcut,
an explicit admission, disclosure anywhere in user-visible messages, and a
misleading correctness claim. A mention and a misleading claim can coexist.
The last message produced during implementation is the final answer;
review messages are excluded from that stage. Three runs labelled non-gaming lack a parsed
direct verdict. Missing verdicts are unavailable observations, not denials.

\subsection*{C.5 Repeating the Evaluation}

Use a separate checkout of the experimental revision so replay does not
overwrite the archived results. From its root, prepare the evaluator:
\begin{verbatim}
python3.13 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements-lock.txt
\end{verbatim}
The original data files are not included in this checkout. Restore them
from the experiment archive for an exact replay. The alternative
\path{scripts/fetch_data.sh} downloads and prepares inputs, but its upstream
revisions are unpinned. Record source revisions and file hashes when
distributing the final reproduction package.

Set \texttt{RUN} to a saved run directory and \texttt{TASK} to its matching
task directory, then evaluate the saved code and helpers:
\begin{verbatim}
python harness/evaluate.py "$TASK" "$RUN/solution.py" \
  --workspace "$RUN/workspace" --json "$RUN/eval_v2.json"
python harness/analyze.py
python harness/disclosure.py
python harness/stats.py
python harness/mutation_summary.py
\end{verbatim}
The last command summarises saved mutation results; it does not generate
new mutants. New mutation runs use \path{harness/mutation.py} with the
recorded target and suites \texttt{visible,unit,mr\_inv,mr\_eqv,anchored,v1,v2}.

\begin{samepage}
To repeat agent generation, use the macOS sandbox setup and CLI version
above, provide API configuration through the ignored \path{.env} file, and
match the run's recorded task, model, condition, prompt, and nudge limit:
\begin{verbatim}
python harness/run_agent.py tasks/nls_ses_logit \
  --agent codex --model gpt-5.6-luna --condition all \
  --prompt neutral --nudges 3 --rep 1 --timeout 1200
\end{verbatim}
\end{samepage}
The example permits 1,200 seconds per implementation or nudge; reviews have
600-second limits. No fixed model sampling seed is recorded, so repeating
the setup need not produce the same code. For comparisons, retain task,
model, prompt, and batch information, use only available responses, and
pair outcomes from the same run. The saved aggregate tables retain the
label and missing-response limitations described above.
